# Автоматизация сделок p2pobmen через СБП ЮKassa

`POST /api/p2pobmen/process-deals` выбирает до 15 сделок `NEW` текущего
пользователя **как продавца**, принимает каждую, создаёт СБП-платёж и отправляет
ссылку в чат. Поддерживается обычный, не доверенный продавец.

Клиент использует маршруты `/api/app/<operation-name>` и заголовок `JWT`, как
опубликованный веб-клиент p2pobmen. Проверено по его схеме 12 ноября 2026 года.
`DealNode.amount` — сумма для перевода продавцу, `amountCurrency.code` — её
валюта. `amountWithdrawal` существует у **лота**, а не у сделки; сумма лота и
`amountLot` для платежа не используются. Только `RUB`, без округления дробных
копеек. Сумма, валюта, чат и тип продавца проверяются до принятия сделки.

## Переменные production

В настройках **того проекта Vercel, который обслуживает web.curvedlines.ru**:

- `P2POBMEN_USERNAME` — логин продавца.
- `P2POBMEN_PASSWORD` — пароль для первичного входа.
- `P2POBMEN_AUTH_TOKEN` — токен сессии, полученный после подтверждения кодом из почты.
- `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` — действующий магазин и ключ.
- `PAYMENT_ADMIN_TOKEN` — Bearer-токен ручного POST/GET.
- `PAYMENT_SIGNING_SECRET` — стабильный секрет ключей идемпотентности.
- `PAYMENT_SITE_URL=https://web.curvedlines.ru`.
- `P2POBMEN_PROCESS_TOKEN` — отдельный случайный секрет запуска через cron-job.org.

Секреты вводить непосредственно в защищённые переменные хостинга. Значения
не хранить в Git и не отправлять в чат. После изменения переменных нужен redeploy.
Не использовать `YOOKASSA_ALLOW_TEST=true` в production.

## Первый вход и код из почты

Для формы с полями ввода запустить **на своём компьютере**:

```sh
npm run p2pobmen:setup
```

Открыть напечатанную ссылку `http://127.0.0.1:4021/#setup=…` на этом же компьютере.
Она содержит временный ключ доступа к локальному помощнику; не публиковать ссылку.
Форма последовательно запрашивает логин, пароль, код из почты и API-ключ
cron-job.org. Пароль, код, JWT и API-ключ не возвращаются в ответах формы.
Веб-сервер слушает только loopback; чужие Origin/Host отклоняются.

Кнопка «Записать переменные в Vercel» переносит четыре P2P-переменные из
закрытого файла в production **только** проекта krivye-linii-web команды
a63909s-projects. CLI должен быть авторизован на том же компьютере:

```sh
npx vercel@65.15.0 login
```

Существующие настройки ЮKassa и подписи не изменяются. После записи переменных
выполнить redeploy проекта. В форме сначала можно подготовить выключенное
задание cron-job.org; кнопка «Проверить сайт и включить» разрешает запуск только
после успешного защищённого `GET /api/p2pobmen/status`. Проверка читает сделки,
не принимает их и не создаёт платежи. После включения планировщик принимает
новые сделки автоматически. Закрыть локальный помощник через Ctrl+C.

Ниже также доступен вариант входа через терминал без браузерной формы.

В терминале владельца запустить `npm run p2pobmen:login`. Помощник последовательно
предлагает логин, скрытый ввод пароля и, если p2pobmen запросил второй фактор,
скрытый ввод кода из почты. Код передаётся в `loginWithCode` вместе с тем же
`challengeId`, который вернул `login`; в переменные среды код не записывается.
Не отправлять пароль, код или JWT в чат.

После успеха `.p2pobmen-auth/env.json` содержит три переменные для переноса в
Vercel, а `.p2pobmen-auth/token` — только JWT. Каталог исключён из Git, файлы
создаются с правами 0600. Они не должны попадать в архивы и артефакты сборки.
Например, при уже настроенном и привязанном Vercel CLI:

```sh
vercel env add P2POBMEN_AUTH_TOKEN production < .p2pobmen-auth/token
```

Если переменная уже существует, использовать `vercel env update`. Ввести
логин и пароль в отдельные защищённые переменные Vercel и выполнить redeploy.

Cron работает только с подтверждённой сессией и **не вызывает вход по паролю**.
Истекающий JWT обновляется через `auth.refreshToken`; свежий JWT кэшируется в
памяти экземпляра. После cold start исходный токен берётся из Environment
Variables. Возможность обновления ограничена политикой p2pobmen: когда исходный
токен перестанет обновляться, снова пройти вход с кодом, заменить
`P2POBMEN_AUTH_TOKEN` и выполнить redeploy. Для бессрочной ротации между
экземплярами понадобится постоянное защищённое хранилище сессии.

## Планировщик

Vercel Cron полностью удалён. Используется бесплатный **cron-job.org**,
запускающий запрос каждую минуту. Vercel остаётся на Hobby.

Форма регистрирует либо обновляет одно задание с такими параметрами:

- URL: `https://web.curvedlines.ru/api/p2pobmen/process-deals`.
- Метод: **POST** (`requestMethod: 1` в API cron-job.org).
- Все минуты, часы и дни, UTC: значения `[-1]` во всех полях расписания.
- Заголовок `Authorization: Bearer <P2POBMEN_PROCESS_TOKEN>`.
- Заголовок `X-P2P-Run-Mode: background`.
- Сохранение тел ответов выключено: в них могут находиться ссылки на платежи.
- Уведомления после трёх ошибок и после восстановления включены.

cron-job.org ждёт ответ не дольше 30 секунд. Endpoint быстро возвращает
**202 `{ "queued": true }`**, а Next.js `after()` продолжает обработку после
ответа в рамках `maxDuration=60`. Успешный ответ планировщику означает запуск
обработки, а не успешное завершение каждой сделки. Итоги и ошибки самой
обработки записываются в журнал Vercel; ошибки `after()` не превращают уже
отправленный 202 в HTTP-ошибку планировщика. Нужен контроль этих журналов.

Пароль p2pobmen и токен администратора в cron-job.org не передаются. Отдельный
токен разрешает только обработку сделок и проверку её готовности. Старый
`CRON_SECRET` поддерживается для GET как совместимость, но новых заданий
Vercel Cron нет. Ручной POST без `X-P2P-Run-Mode` по-прежнему возвращает итог
обработки синхронно.

Задание не включается, пока не настроены сессия, ЮKassa и секреты сервера.
Проверка готовности не заменяет первую проверку оплаты в живой сделке.

Обработчик прекращает брать новые сделки, если оставшегося времени недостаточно
для внешних запросов; оставшиеся `NEW` попадут в следующий запуск.
Не включать production cron на preview с рабочими учётными данными.

API планировщика: https://docs.cron-job.org/rest-api.html.
Лимит ожидания: https://cron-job.org/en/faq/.

## Уведомления и повторная доставка

В ЮKassa настроить `https://web.curvedlines.ru/api/yookassa/webhook` на события
`payment.succeeded`, `payment.canceled`. Webhook повторно запрашивает платёж
через API и проверяет магазин, тестовый режим, источник, сумму, валюту, номер
заказа и привязку к сделке. Затем запрашивает собственную сделку продавца,
сверяет сумму и чат, вызывает **confirmPaymentRecieve**.

`CLOSED` и `PAID_CONFIRMED` считаются уже подтверждёнными. Ошибка API,
неподходящий статус или пустой результат подтверждения возвращают не-200,
чтобы ЮKassa повторила уведомление. Возврат браузера на сайт не подтверждает оплату.
Обычные платежи `source=curvedlines-web` продолжают обрабатываться.

Ключ платежа привязан к полному UUID сделки (`p2p-<UUID>`), без усечения.
При повторном запросе с тем же телом ЮKassa переиспользует платёж в пределах
срока хранения ключа (24 часа). `PAYMENT_SIGNING_SECRET` во время работы менять
нельзя: это изменит ключи идемпотентности.

## Ошибки после принятия сделки

Ответ с `results[].status=error` имеет HTTP 502; в элементах сохраняются
`dealId`, `acceptedState` и, если уже создан, `paymentId`. В журналах также есть
идентификаторы проблемных сделок. Ошибка одной сделки не прерывает остальные.

Сделка, принятая до сбоя ЮKassa или чата, уже не `NEW` и **автоматически повторно
не выбирается**. Проверить её в p2pobmen и ЮKassa; если платёж создан — отправить
его существующую ссылку в чат вручную. Не создавать второй платёж вслепую,
особенно после 24 часов. Для полного автоматического восстановления таких
сделок требуется постоянный реестр этапов обработки, которого в проекте нет.

## Проверка после деплоя

В защищённом терминале, где задан `PAYMENT_ADMIN_TOKEN`:

```sh
curl --fail-with-body -X POST https://web.curvedlines.ru/api/p2pobmen/process-deals \
  -H "Authorization: Bearer ${PAYMENT_ADMIN_TOKEN}"
```

Этот запрос принимает реальные `NEW` сделки и создаёт платежи. Проверить ответ,
ссылку в чате, точную сумму и RUB. После оплаты через СБП проверить в ЮKassa
`succeeded`, в логах успешный `confirmPaymentRecieve` и статус сделки в p2pobmen.
Повторная доставка того же уведомления не должна повторно подтверждать сделку.

Локальные проверки: `node --test tests/*.test.mjs`, `npm run lint`,
`npx tsc --noEmit`, `npm run build`. Тесты заменяют внешние HTTP-ответы и не
создают реальные платежи. Для проверки с действующими сервисами нужны
production-переменные и доступ к проекту хостинга.
