# Персональные ссылки и постоянная страница оплаты

Для каждого отклика обработчик создаёт отдельный платёж и автоматически
отправляет в его чат короткую ссылку
`https://web.curvedlines.ru/pay/sbp/<UUID-платежа>`.
Чат площадки не превращает URL в ссылку. Основной путь — ссылка под QR-кодом;
персональный URL в сообщении остаётся запасным вариантом для копирования
в браузер. PDF-вложения не используются.
На телефоне открывается выбор банка с суммой этой сделки, на компьютере —
страница оплаты с QR. Другие неоплаченные заявки не блокируют переход.

Ссылка передаёт проверенный UUID в существующий обработчик как `payment:<UUID>`.
Он запрашивает платёж отдельным GET по его ID, сверяет магазин, источник,
собственную сделку продавца, сумму, RUB, чат, статус и срок действия. Поиска
по общему списку платежей и выбора из активных заявок здесь нет.
Этот путь только читает данные и не создаёт новых платежей.

Постоянный QR содержит `https://web.curvedlines.ru/pay`. Тот же URL указывается
в поле «Ссылка для оплаты» в реквизитах лота. При одной принятой неоплаченной сделке продавца страница
сразу перенаправляет на **уже созданный** платёж ЮKassa: выбор банка с готовой
суммой, без формы ввода ID и без дополнительной кнопки на нашем сайте.
Страница не создаёт платежи, не принимает
сделки, не отправляет сообщения и не подтверждает получение денег.
Существующие обработчики и их конфигурация не изменены.

Общая ссылка не передаёт идентификатор покупателя. Для проверки запрашиваются
две сделки в состояниях ACCEPTED/PAID. Если найдено несколько, страница показывает
до 15 ожидающих сделок: номер, полный ID и сумму, без контактов покупателя.
Покупатель выбирает свою сделку или вводит её номер/полный ID в форму. Поиск
по номеру ограничен собственными ожидающими сделками продавца; закрытые и
исторические сделки по короткому номеру не выдаются. Так можно найти сделку,
которая не попала в первые 15 записей. Вводится номер, а не сумма.

На `/pay/choose?order=...` сервер проверяет существующий платёж, а покупатель
сверяет номер и сумму с чатом площадки и ставит обязательную отметку подтверждения.
Кнопка оплаты повторно проверяет состояние сделки и платежа, номер и сумму.
При изменении данных переход блокируется. Даже пять одинаковых сумм относятся
к разным номерам/ID. Обновление списка через `?choose=1` сохраняет явный выбор,
даже если осталась только одна сделка; автоматического выбора по очереди нет.
Если платёж ещё готовится, браузер последовательно проверяет готовность
до 90 секунд; запросы не накладываются. Затем можно повторить проверку кнопкой.
Логика выбора вынесена в read-only `GET /api/pay/active`.
Персональная ссылка `/pay?ref=<UUID-заявки>` сразу открывает нужный платёж.
Она сохранена для совместимости; новые сообщения содержат `/pay/sbp/<UUID-платежа>`.
Персональные ссылки по-прежнему требуют полного UUID. Поиск короткого номера
и публичный список доступны только в новом явно выбранном сценарии ожидания
оплаты и не возвращают историю или личные данные покупателей.

Перед редиректом сервер повторно читает собственную заявку продавца и сверяет её сумму, RUB, состояние,
номер, чат и метаданные с существующим платежом этого магазина. При поиске
по UUID просматриваются максимум три страницы по 100 платежей за последние
7 дней. Если весь диапазон не просмотрен, данных недостаточно или платежей
несколько, переход к оплате блокируется; нужно использовать персональную
ссылку из чата. Цена из query-параметров никогда не принимается.

Закрытые заявки, полученная оплата, истёкшие и отменённые платежи не предлагают
повторную оплату. Если платёж ещё не создан существующей системой, страница
предлагает дождаться ссылки. Рабочую автоматику, расписания и секреты этот
интерфейс не включает и не перенастраивает.

Новые переменные среды не требуются. Используются существующие настройки
магазина и подтверждённой сессии продавца. Значения не попадают в браузер.
Страница не индексируется через существующий layout `/pay`, все внешние
запросы используют `no-store`. Проверять с реальными сервисами только
чтение; для тестов внешние ответы заменяются заглушками.
